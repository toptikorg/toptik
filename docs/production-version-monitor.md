# Production version monitoring

The independent `production-version` job compares the public Git commit in `/api/build-version` on each of the landing, admin and site hostnames to the current `master` reference in the public GitHub repository. It does not call Shopify or use a Vercel token. The endpoint returns only the 40-character `VERCEL_GIT_COMMIT_SHA` and sets `Cache-Control: no-store`. Missing or invalid metadata returns 503.

A mismatch is rechecked against GitHub to distinguish a branch update during the check. A mismatch, missing endpoint, invalid response, GitHub rate limit or network error produces a failed check and a separate incident with evidence. The latter cases are inconclusive, not proof of a stale deployment. A normal deployment may temporarily report a mismatch; verify deployment progress before reacting. A later verified match closes this incident. The job does not automatically deploy, reassign aliases, or prevent stale deployments.

Important limitations: this observes each hostname from the runner at one moment. It does not verify every edge region, build contents, or protection against forged deployment metadata. Comparing the reported SHA cannot prove source integrity. Existing old deployments lack the endpoint and return 404, correctly reported as unavailable. The endpoint and monitor must first be deployed on a supported Vercel Git deployment and tested; Vercel must expose its system commit environment variable. Until then this check cannot establish a match. An intentional rollback to an older commit will also alert and requires documented handling. Separate release controls are required to prevent stale promotion.
