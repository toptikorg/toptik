# Shopify ↔ Gallery visible-copy synchronization

**Status:** implementation candidate in Draft PR #19; not active and not production-verified. This stage synchronizes customer-visible product title, description, SEO title, and SEO description for one verified product in both directions. It is a staged subset of the requested full product synchronization, not completion of that request.

**Existing Shopify connection verified on 2026-09-30:** the earlier bulk uploader used the Shopify Admin GraphQL API, not FTP. A read-only client-credentials exchange using its existing Windows-encrypted credentials succeeded against `toptikcoil.myshopify.com`; Shopify returned store `Toptik.co.il`, primary domain `www.toptik.co.il`, and the installed app's `write_products` scope. No product mutation was performed and no secret was printed or saved. The historical uploader must not be rerun wholesale. The current server candidate reuses the same authentication method with automatic token renewal. The local encrypted credential file does not configure Vercel automatically: server secrets, signed webhook subscriptions, the database migration, and a live two-way round trip are still outstanding.

## Field ownership and merge contract

| Data | Authority and behavior |
|---|---|
| Product title, visible description, SEO title, SEO description | Bidirectional, field-by-field merge. A one-sided edit propagates automatically to the other system. |
| Price, currency, inventory, sale status, variant/SKU identity, handle, publication | Shopify remains authoritative. This integration never writes these fields from Gallery. |
| Manufacturer specs, Gallery images/angles, brand/category/filter state, display order | Gallery/manufacturer workflow remains authoritative; not copied to Shopify by this copy-sync path. |

Merge behavior — field-by-field, with no silent data loss:

1. The sync unit is exactly one unique Gallery SKU row ↔ one Shopify product. The Gallery SKU must match exactly after whitespace/punctuation normalization and the already verified optional Mandarina Duck `-TU` suffix rule. No fuzzy title, color, image, handle, or partial-SKU matching is allowed. Missing, duplicate, changed, or many-to-one identities are quarantined; no copy is written until identity is unambiguous.
2. For each bound product, compare `title`, normalized customer description, `seoTitle`, and `seoDescription` separately against the last successfully agreed snapshot. A change in one field never grants permission to replace another field. `null` and empty SEO text are treated as an intentional empty value after binding; clearing a field propagates as a clear. A missing field in an older Gallery client payload means “not supplied” and preserves the stored value; it is not a clear operation.
3. Initial binding stores independent Gallery and Shopify snapshots for every field. If one side alone has a non-empty value, copy it to the empty side. If both sides already have different non-empty values, preserve both and record each as its own baseline; do not overwrite either side or label historical differences as new edits. This lets the one-product canary proceed without destroying existing copy or requiring an operator to choose a historical winner.
4. After baseline: compare each side to its own last-synced snapshot. If only Gallery changed a field, propagate that value to Shopify; if only Shopify changed it, propagate it to Gallery. Untouched historical differences remain untouched. If both changed the same field since baseline, compare Gallery `copy_updated_at` with Shopify product `updatedAt`; the later timestamp wins that field, and both source values plus timestamps and decision are written to the private deduplicated conflict audit. Exact ties, invalid timestamps, or missing timestamps resolve deterministically to Shopify and are audited. This is automatic for ordinary edits; identity ambiguity remains quarantined.
5. Timestamp caveat: Shopify exposes a product-level `updatedAt`, not a timestamp per copy field. An unrelated Shopify product edit can advance it. Therefore this rule is deterministic and protects non-overlapping edits, but simultaneous same-field edits have best-available—not perfect—ordering. We never claim true chronological last-writer-wins. Shopify wins ties/unknown ordering, and both versions remain in the audit.
6. A Gallery-originated write re-reads Shopify immediately before mutation and re-runs the merge if the snapshot changed. If another write still makes the candidate unsafe, stop and retry/review rather than overwrite. Shopify `productUpdate` has no atomic compare-and-swap token, so a very narrow third-party edit race remains between the final read and mutation; that limitation is explicit.
7. Shopify rich description HTML is rendered as safe readable plain text in the current Gallery editor. Only fields that actually differ from the final Shopify snapshot are sent to `productUpdate`: a title-only or SEO-only change leaves `descriptionHtml` absent from the mutation and preserves its original formatting, links, and tables. If a Gallery user actually edits that description, the Gallery plain-text paragraphs become Shopify paragraph HTML; original rich formatting cannot be round-tripped by the current editor. Do not claim lossless rich-text sync. The current one-product verification must use a description whose safe paragraph representation is equivalent; general rollout still needs a lossless rich-text strategy.
8. Webhooks are signed, deduplicated triggers—not ordered truth. Every worker fetches the latest Shopify snapshot and reads the latest Gallery row; stale/replayed/out-of-order queue bodies never become content. Idempotent hashes avoid echo loops. Transient API/database errors retry with bounded attempts; permanent/identity/validation/readback conflicts stop in a private review/failure queue and never silently drop the source values.
9. Before and after every write, validate exact product/variant/SKU binding and allowed field set. Shopify writes are restricted to product `title`, `descriptionHtml`, and `seo.title/description`. Gallery writes are restricted to those four copy columns. Price, currency, inventory, availability/status, variant/SKU, handle, media, publication, manufacturer specs, filter/category, display order, and product existence are outside this contract and are never overwritten by this sync.
10. A Shopify deletion/unpublish deactivates only the verified Gallery purchase binding; it does not delete a Gallery row or its copy. A Shopify product that disappears, an image failure, or a missing variant never creates a blank public card. Shopify product creation does not automatically create a public Gallery item because an exact SKU alone cannot verify image, manufacturer data, category, or moderation state.
11. A stale Gallery copy save is rejected against `copy_updated_at`; reload is required before saving. The database checks that version under row locks and saves copy plus its outbox entry in one transaction. A failed outbox insert rolls back that copy save. A five-minute product lease serializes inbox and outbox reconciliation and excludes competing Gallery copy saves; a busy worker requeues without consuming a retry attempt. A missing RPC after migration fails closed instead of falling back to a non-atomic upsert. Existing settings/angle handling is separate from the copy transaction; do not describe the entire editor save as atomic.
   During this candidate stage, a migrated full-catalog save cannot implicitly delete an omitted existing item: it returns `SYNC_GALLERY_DELETE_REQUIRES_ARCHIVE`. Use the existing inactive state to hide a product. An explicit, versioned archive/delete workflow remains follow-up work; a stale editor must not delete a newly added product or a product being synchronized.
12. “Automatic” means normal, unambiguous edits propagate without double entry after setup. Initial conflicting copies, uncertain identity, many-to-one product mappings, unsupported rich formatting, exhausted retries, or concurrent write races are explicit exceptions: the system preserves source values and holds the affected item instead of guessing or overwriting.

The four synchronized fields cover the first copy-and-SEO stage only. The full user request also includes new product creation and all shared fields. Those remain required follow-up work, with exact SKU identity, verified product images, field ownership, and no destructive replacement of existing values. Price/currency/availability remain Shopify-authoritative under the project rules; changes made through the Gallery need to be routed to the authoritative Shopify variant and read back, not copied from old supplier data.

## Candidate implementation

- Signed `/api/webhooks/shopify/products` endpoint validates the raw-body HMAC, expected shop, allowed topic, bounded body, and unique delivery ID before storing a private inbox row.
- Exact SKU reconciliation updates private bindings and the small public product-link projection only. Unpublished handles and variant IDs are scrubbed from that public projection.
- Gallery admin now carries separate SEO title/description fields and queues actual visible-copy edits. Shopify Admin GraphQL updates only product `title`, `descriptionHtml`, and `seo`; it does not update price, inventory, variants, handle, media, status, or publication.
- Shopify product-update events fetch and reconcile the latest visible copy back into the Gallery.
- Shopify webhook and Gallery-save responses schedule the worker immediately. A daily guarded Vercel cron is a recovery sweep; it does nothing useful until the migration and required Shopify secrets/subscriptions are installed.
- Private conflict audit, retry queues, bounded status endpoint, stale-claim handling, product reconciliation leases, atomic copy/outbox saves, idempotent content hashes, and public-link projection are in the candidate migration/code.
- Inbox failures use their `processed_at` column; outbox failures do not attempt to write that nonexistent column. Each failed row is recorded without stopping later rows in the batch.
- Client-credentials tokens are cached only in server memory, renewed before expiry, shared across concurrent requests, and replaced after credential rotation. Token requests reject redirects and never cache HTTP responses. Missing scopes, malformed responses, and upstream errors fail closed without logging secret response bodies.
- If the sync migration is absent, existing Gallery saves retain legacy fallbacks but no Shopify sync is active. After migration, a failed outbox insert rolls back the copy mutation.

## Not covered by this implementation

- Automatic creation of a new Gallery item for every new Shopify product. A verified matching image, manufacturer data, brand/category, and moderation/publication state are still required before a new product can appear publicly.
- Bidirectional price/inventory sync. Shopify remains their source of truth; the Gallery currently links to the exact live Shopify product/variant.
- Per-variant SEO/title fields. Shopify exposes the product title/description/SEO at product level. Products with multiple Gallery rows must not use each row as a separate writer; those mappings are held from copy sync.
- In-app conflict editing UI. Normal and same-field concurrent edits resolve automatically; private audit rows retain the losing value. Operational status is available to authenticated admin only.
- A conflict-resolution action/UI for the private concurrent-edit audit. Initial differences are preserved as side-specific baselines and do not block the canary; simultaneous same-field edits are resolved deterministically and the losing source value remains in the private audit.
- Live end-to-end verification. Existing Shopify authentication and product-write permission are verified, but server configuration, signed webhooks, and the database migration are not activated. No real Shopify write has been attempted by this candidate.

## Required setup and release gates

### One-product production canary gate

- The first live activation must set SHOPIFY_SYNC_CANARY_SKU to exactly one verified SKU. Missing, malformed, comma-separated, or semicolon-separated values disable the worker; no broad allowlist is accepted.
- Webhook reconciliation and Gallery outbox writes are restricted to that normalized exact SKU. Other product events are acknowledged without catalog writes. Delete events for the canary are held for review and never deactivate it during the canary.
- The bootstrap endpoint accepts one Shopify product ID, reads that product, verifies it has exactly one variant and that variant matches the configured canary SKU, and queues only that product. It never scans or queues the whole Shopify catalog. A matching SKU inside a multi-variant product is rejected because its copy is shared with sibling variants.
- Keep the SKU canary active through both directions and live readback. Only after the one-SKU round-trip passes should a separately reviewed rollout change expand the eligible catalog.
- The canary gate limits which product the worker can mutate; it does not replace correct Shopify app scopes, signed webhooks, server-side secrets, or Supabase protections.

1. Reuse the verified installed app when its existing access covers the operation. No new app installation or permission expansion is needed for this copy stage. The legacy app has broader permissions for its historical publishing tasks; the sync implementation must exercise only the required product reads/updates.
2. Securely configure `SHOPIFY_SHOP_DOMAIN`, `SHOPIFY_CLIENT_ID`, `SHOPIFY_CLIENT_SECRET`, `SHOPIFY_WEBHOOK_SECRET` for that same app, `SHOPIFY_ONLINE_STORE_PUBLICATION_ID`, `SHOPIFY_API_VERSION`, and the single `SHOPIFY_SYNC_CANARY_SKU` on the server. Client credentials produce short-lived access tokens automatically; do not paste a temporary token into long-lived configuration. Never log or document secret values.
3. Execute the migration checks locally first, then apply the additive migration to the existing Supabase project using authorized administration access. Verify RLS/grants, queue claims, conflict deduplication, atomic copy/outbox behavior, lease exclusion, and public projection. This does not require purchasing or creating another environment. Local SQL validation does not prove the migration is applied in Production.
4. Register signed Shopify webhooks for product create/update/delete. Confirm actual webhook payloads and Shopify SEO fields are available from the Admin API snapshot.
5. Seed existing catalog bindings in a controlled bootstrap, then test single and multiple variants/products, exact SKU normalization, duplicate/missing/unmatched SKU, initial copy adoption, blank SEO values, edits in both directions, disjoint edits, simultaneous same-field changes, timestamp ties, stale/reordered webhook deliveries, deletion/unpublish, HTML entities/formatting, Shopify throttling, worker retries, stale admin save rejection, and read-back.
6. Verify customer-facing Shopify pages and Gallery items live after each round trip, and confirm protected commerce fields do not change. Test rollback and re-run/idempotency.
7. Use the already authorized one-product live test after server configuration and migration are verified. Snapshot that product before changes, make reversible edits one direction at a time, verify actual public product pages and stored fields, restore test edits, and keep the single-SKU restriction through the readback. Do not claim automatic catalog-wide synchronization from a one-product success.

## Remaining scope after the canary

- New product creation from either system, with duplicate prevention, real images matched to SKU/color, category mapping, and publication rules. The current candidate binds existing products only.
- Shared images, specs and other editable fields, with documented authoritative source per field and a lossless rich-description representation.
- Product-level copy versus variant-level SKU/price/inventory handling for products with multiple variants.
- Full eligible-catalog rollout, end-to-end replay/concurrent-edit checks, and ongoing reconciliation without manual duplicate entry.
- Production proof for each supported direction and field. Existing article/indexing settings are independent and must remain unchanged by sync deployment.

## Verification for the current candidate

- Full local suite: 171/171 tests passed; changed-file ESLint and the real Next production build passed.
- SQL was executed against local PostgreSQL via PGlite, including the complete migration and an idempotent second application. The fixture installs `pgcrypto` in `extensions`, as in common Supabase setups; the new outbox hash uses PostgreSQL's built-in SHA-256 so it does not depend on that extension's schema.
- SQL checks cover row creation/update, unchanged-copy idempotence, metadata preservation, stale-version rejection, deletion rejection, exclusive leases and release ownership, editor exclusion while a worker is active, rollback when outbox insertion fails, and denial of private tables/RPCs to anonymous/authenticated clients. Required direct worker operations were executed as `service_role`; grants are explicit rather than dependent on Supabase defaults. Binding/projection writes and lease ownership remain RPC-only.
- Reproduce SQL checks with `node scripts/verify-shopify-sync-sql.mjs <local-PGlite-package-directory>`. PGlite was used only as a local validation tool; no application dependency or paid external environment was added.
- These results verify the candidate code and SQL. They do not mean Supabase Production has this migration, or that Shopify and Gallery exchange live edits.
