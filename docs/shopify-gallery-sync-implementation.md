## Field ownership and merge contract

| Data | Authority and behavior |
|---|---|
| Product title, visible description, SEO title, SEO description | Bidirectional, field-by-field merge. A one-sided edit propagates automatically to the other system. |
| Price, currency, inventory, sale status, variant/SKU identity, handle, publication | Shopify remains authoritative. This integration never writes these fields from Gallery. |
| Manufacturer specs, Gallery images/angles, brand/category/filter state, display order | Gallery/manufacturer workflow remains authoritative; not copied to Shopify by this copy-sync path. |

Merge behavior — field-by-field, with no silent data loss:

1. The sync unit is exactly one unique Gallery SKU row ↔ one Shopify product. The Gallery SKU must match exactly after whitespace/punctuation normalization and the already verified optional Mandarina Duck `-TU` suffix rule. No fuzzy title, color, image, handle, or partial-SKU matching is allowed. Missing, duplicate, changed, or many-to-one identities are quarantined; no copy is written until identity is unambiguous.
2. For each bound product, compare `title`, the atomic description pair (`description` plus `descriptionHtml`), `seoTitle`, and `seoDescription` separately against the last successfully agreed snapshot. A change in one field never grants permission to replace another field. HTML-only link or formatting edits count as description edits even when displayed text is unchanged. `null` and empty SEO text are treated as an intentional empty value after binding; clearing a field propagates as a clear. A missing field in an older Gallery client payload means “not supplied” and preserves the stored value; it is not a clear operation. Description HTML has its own legacy rule: `null`/missing means uninitialized, while `""` is an explicit clear.
3. Initial binding stores independent Gallery and Shopify snapshots for every field. If one side alone has a non-empty value, copy it to the empty side. If both sides already have different non-empty values, preserve both and record each as its own baseline; do not overwrite either side or label historical differences as new edits. This lets the one-product canary proceed without destroying existing copy or requiring an operator to choose a historical winner.
4. After baseline: compare each side to its own last-synced snapshot. If only Gallery changed a field, propagate that value to Shopify; if only Shopify changed it, propagate it to Gallery. Untouched historical differences remain untouched. If both changed the same field since baseline, compare Gallery `copy_updated_at` with Shopify product `updatedAt`; the later timestamp wins that field, and both source values plus timestamps and decision are written to the private deduplicated conflict audit. Exact ties, invalid timestamps, or missing timestamps resolve deterministically to Shopify and are audited. This is automatic for ordinary edits; identity ambiguity remains quarantined.
5. Timestamp caveat: Shopify exposes a product-level `updatedAt`, not a timestamp per copy field. An unrelated Shopify product edit can advance it. Therefore this rule is deterministic and protects non-overlapping edits, but simultaneous same-field edits have best-available—not perfect—ordering. We never claim true chronological last-writer-wins. Shopify wins ties/unknown ordering, and both versions remain in the audit.
6. A Gallery-originated write re-reads Shopify immediately before mutation and re-runs the merge if the snapshot changed. If another write still makes the candidate unsafe, stop and retry/review rather than overwrite. Shopify `productUpdate` has no atomic compare-and-swap token, so a very narrow third-party edit race remains between the final read and mutation; that limitation is explicit.
7. Shopify raw rich HTML is retained alongside plain display text, including links and tables. Only fields that actually differ from the final Shopify snapshot are sent to `productUpdate`: a title-only or SEO-only change leaves `descriptionHtml` absent and preserves its original bytes. An intentional rich edit sends the validated HTML and derives its plain projection with a real HTML parser. A description conflict chooses and audits one complete text/HTML pair; it never combines one side's text with the other side's markup. Parser-normalized equivalent HTML is accepted on Shopify readback; the actual returned raw HTML is saved as the Shopify baseline and the Gallery raw HTML as its own baseline, preventing formatting-only echo loops. The isolated admin editor supports visual editing and HTML source mode; public Gallery cards still render escaped plain text. This implements rich-description retention, not a claim that all possible active or unsafe HTML is editable.
8. Webhooks are signed, deduplicated triggers—not ordered truth. Every worker fetches the latest Shopify snapshot and reads the latest Gallery row; stale/replayed/out-of-order queue bodies never become content. Idempotent hashes avoid echo loops. Transient API/database errors retry with bounded attempts; permanent/identity/validation/readback conflicts stop in a private review/failure queue and never silently drop the source values.
9. Before and after every write, validate exact product/variant/SKU binding and allowed field set. Shopify writes are restricted to product `title`, `descriptionHtml`, and `seo.title/description`. Gallery writes are restricted to the same four logical fields, with the description stored in the paired `description` and `description_html` columns. Price, currency, inventory, availability/status, variant/SKU, handle, media, publication, manufacturer specs, filter/category, display order, and product existence are outside this contract and are never overwritten by this sync.
10. A Shopify deletion/unpublish deactivates only the verified Gallery purchase binding; it does not delete a Gallery row or its copy. A Shopify product that disappears, an image failure, or a missing variant never creates a blank public card. Shopify product creation does not automatically create a public Gallery item because an exact SKU alone cannot verify image, manufacturer data, category, or moderation state.
11. A stale Gallery copy save is rejected against `copy_updated_at`; reload is required before saving. The database checks that version under row locks and saves copy plus its outbox entry in one transaction. A failed outbox insert rolls back that copy save. A five-minute product lease serializes inbox and outbox reconciliation and excludes competing Gallery copy saves; a busy worker requeues without consuming a retry attempt. A missing RPC after migration fails closed instead of falling back to a non-atomic upsert. Existing settings/angle handling is separate from the copy transaction; do not describe the entire editor save as atomic.
   During this candidate stage, a migrated full-catalog save cannot implicitly delete an omitted existing item: it returns `SYNC_GALLERY_DELETE_REQUIRES_ARCHIVE`. Use the existing inactive state to hide a product. An explicit, versioned archive/delete workflow remains follow-up work; a stale editor must not delete a newly added product or a product being synchronized.
12. “Automatic” means normal, unambiguous edits propagate without double entry after setup. Initial different nonempty copies are retained as independent baselines. Uncertain identity, many-to-one product mappings, unsafe edited HTML, exhausted retries, or concurrent write races are explicit exceptions: the system preserves source values and holds the affected item instead of guessing or overwriting.

### Rich-description editor, compatibility, and limits

- The authenticated editor receives raw `descriptionHtml`; public repository responses omit it. The public Gallery continues to display escaped plain text, without injecting Shopify HTML into the public page.
- Visual editing runs inside a sandboxed iframe with `allow-same-origin` but no `allow-scripts`, and an immutable CSP that denies scripts, connections, forms, and embedded frames/objects. Product HTML is never interpolated into the iframe `srcdoc` or injected into the outer admin DOM. The parent installs editor handlers; links cannot navigate from the editor. HTML source mode allows deliberate corrections while retaining unsupported original source.
- Mounting, opening/closing the editor, switching modes, or changing an unrelated field does not emit a description edit or serialize the original markup. Validated intentional changes preserve supported passive markup, links, and tables. Unsafe edits and paste content are rejected visibly rather than silently stripped. Existing unsafe markup remains stored and can be viewed as source, but cannot be rendered in the visual editor or submitted as a new unsafe edit.
- Deliberately edited HTML is limited to **200,000 JavaScript string units**, checked by `assertSafeDescriptionHtml`; the source textarea has the same limit. The request schema permits **250,000** units for `descriptionHtml` so an unchanged existing raw value can travel through a save without being truncated or rewritten. That larger transport allowance does not authorize new HTML above the edit limit. Raw HTML above the transport limit cannot pass a full save and must be handled explicitly; it is never silently shortened. Plain description transport allows 50,000 units.
- An old client that omits HTML and keeps the description unchanged preserves stored rich HTML byte-for-byte. An old client that changes only plain text while rich HTML already exists receives `SYNC_DESCRIPTION_RICH_EDITOR_REQUIRED` and must reload the current editor. Missing legacy HTML with unchanged text stays uninitialized; a deliberate plain edit without an existing rich document generates escaped paragraph HTML and derives the paired text consistently. Old sync baselines hydrate HTML without interpreting its former absence as a clear or an edit. Reviewed-copy repairs cannot replace the plain description independently once a rich pair exists.
- The additive migration stores `description_html`, includes both members in copy versions/outbox records, and records both values together in description conflict audit entries. Before that rich column exists, legacy reads/saves retain their established fallback; explicit rich saves fail closed and require the migration.
- Full Gallery saves accept at most **5,000 items**. The **80-row** limit remains solely on an individual Excel/manufacturer import batch to bound upstream requests; it is not a total catalog limit and must not truncate a normal save of the existing catalog.

The four synchronized fields cover the first copy-and-SEO stage only. The full user request also includes new product creation and all shared fields. Those remain required follow-up work, with exact SKU identity, verified product images, field ownership, and no destructive replacement of existing values. Price/currency/availability remain Shopify-authoritative under the project rules; changes made through the Gallery need to be routed to the authoritative Shopify variant and read back, not copied from old supplier data.

## Candidate implementation

- Signed `/api/webhooks/shopify/products` endpoint validates the raw-body HMAC, expected shop, allowed topic, bounded body, and unique delivery ID before storing a private inbox row.
- Exact SKU reconciliation updates private bindings and the small public product-link projection only. Unpublished handles and variant IDs are scrubbed from that public projection.
- Gallery admin carries separate SEO title/description fields, the isolated rich-description editor, and queues actual visible-copy edits. Text/HTML descriptions merge and persist as one logical field. Shopify Admin GraphQL updates only product `title`, `descriptionHtml`, and `seo`; it does not update price, inventory, variants, handle, media, status, or publication.
- Shopify product-update events fetch and reconcile the latest visible copy back into the Gallery.
- Shopify webhook and Gallery-save responses schedule the worker immediately. A daily guarded Vercel cron is a recovery sweep; it does nothing useful until the migration and required Shopify secrets/subscriptions are installed.
- Private conflict audit, retry queues, bounded status endpoint, stale-claim handling, product reconciliation leases, atomic copy/outbox saves, idempotent content hashes, and public-link projection are in the candidate migration/code.
- Inbox failures use their `processed_at` column; outbox failures do not attempt to write that nonexistent column. Each failed row is recorded without stopping later rows in the batch.
- Client-credentials tokens are cached only in server memory, renewed before expiry, shared across concurrent requests, and replaced after credential rotation. Token requests reject redirects and never cache HTTP responses. Missing scopes, malformed responses, and upstream errors fail closed without logging secret response bodies.
- If the sync migration is absent, existing Gallery saves retain legacy fallbacks but no Shopify sync is active. After migration, a failed outbox insert rolls back the copy mutation.

## Not covered by this implementation

- Automatic creation of a new Gallery item for every new Shopify product. A verified matching image, manufacturer data, brand/category, and moderation/publication state are still required before a new product can appear publicly.
- Bidirectional price/inventory sync. Shopify remains their source of truth; the Gallery currently links to the exact live Shopify product/variant.
- Per-variant SEO/title fields. Shopify exposes the product title/description/SEO at product level. Products with multiple Gallery rows must not use each row as a separate writer; those mappings are held from copy sync.
- In-app conflict editing UI. Normal and same-field concurrent edits resolve automatically; private audit rows retain the losing value. Operational status is available to authenticated admin only.
- A conflict-resolution action/UI for the private concurrent-edit audit. Initial differences are preserved as side-specific baselines and do not block the canary; simultaneous same-field edits are resolved deterministically and the losing source value remains in the private audit.
- Full-catalog end-to-end verification remains open. The one-product copy round trip is now verified live, as recorded below; it does not prove new-product, media/specification or full-field synchronization.
