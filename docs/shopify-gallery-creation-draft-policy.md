# Gallery → Shopify: new private draft lane

Implemented locally on `c6b5ef0`; **not deployed or enabled**. Existing 78 approved products, copy queues, stock, publications, SEO visibility and public Gallery remain unchanged.

## Executable path

1. The private editor at `/admin/shopify/new-product` saves incomplete input through `PUT /api/admin/shopify/creation-intents` with `{input, expectedRevision}`. It records server-derived edit provenance and performs atomic revision CAS without creating a public Gallery item. When required draft information is complete, the server automatically promotes that exact revision to an **inactive** Gallery row, ordered angles and the durable draft worker. The existing completed DTO endpoint `POST /api/admin/shopify/drafts` remains restricted to an identical manufacturer/store SKU without mapping; differing identifiers must use a server-owned mapping receipt through pending-intent promotion. Both the endpoint and SQL enforce this boundary. Repeating the same UUID/source returns that intent; another UUID with the same normalized SKU is refused.
2. `schedule-creation.ts` starts a bounded worker after the response, with at most eight fixed-origin continuation wakeups. `PATCH` resumes the same UUID; `GET ?id=<uuid>` gives private status and Shopify IDs without source/commerce bodies. The editor can resume a frozen nonterminal draft using its unchanged UUID/revision; it cannot replace its frozen source. An out-of-order response cannot replace the currently selected editor state. Pending-intent request work has a shared nine-second deadline, and worker cleanup plus continuation are reserved within an absolute 55-second request budget. OAuth and GraphQL share that absolute deadline, checked again after authentication.
3. `creation-runtime.ts` reads actual shop currency, installed app identity and its pre-existing unique PRODUCT `id` definition; scans all variant statuses and Gallery active/inactive rows; downloads and decodes exact image bytes. `creation-policy.ts` freezes source plus image identity. No supplier price, guessed inventory, generic image or manufacturer SKU substitution is accepted.
4. The SQL lease/source CAS records `create_started` **before** the only `productCreate` call. The mutation includes DRAFT status and app-owned custom ID `toptikcoil.myshopify.com:gallery:<UUID>` plus frozen source hash. No productSet/upsert, collections, inventory or publication mutation exists.
5. Initial response IDs, commercial values and version are recorded immutably. Before configuring only the returned default variant, a fresh read must match both product version and the initial commercial fingerprint. Known selling price/barcode/tax fields are applied; omitted fields retain their original values. The request is recorded as `variant_started` before sending.
6. A fresh exact readback checks copy, SKU, all commercial fields, unpublished DRAFT status, and ordered Shopify images against the frozen hashes. SQL stores that evidence atomically before `draft_ready`. Gallery remains inactive and unbound; no existing approval/baseline record changes.

## Activation boundary

- Requires `VERCEL_ENV=production` **and** `SHOPIFY_GALLERY_CREATE_MODE=draft_only`. Missing/off/Preview is refused before reservations or Shopify mutations.
- Apply the additive `20260930_gallery_shopify_draft_creation.sql`, then `20260930_gallery_shopify_pending_intents.sql`, only after review. Applying schema alone does not ingest or create products.
- Requires actual installed app's `app--<app-id>--toptik_gallery.source_item_id` PRODUCT metafield definition, type `id`, uniqueness enabled. This implementation reads it and refuses absence; it never silently installs a definition or requests permissions.
- Uses existing server-side app credentials and service-role client. Every HTTP entry requires the existing admin token. No client receives secrets, private readiness evidence or GraphQL access.
- The existing Gallery editor has a link to the separate private new-product editor. Its original Add Item/full-catalog save and import routes are **not yet wired** to pending intents. Ordinary existing-item saves never create a product implicitly. Completing that normal creation/import flow remains required for the requested automatic workflow.

## Recovery and preservation

- A lost create response is reconciled by the custom ID; creation is **never resent** after a started/uncertain receipt. When the initial commercial response cannot be proved, the owned draft is placed under review rather than guessed or overwritten.
- A lost variant response is reconciled through actual readback; configure is not resent. A changed merchant price, tax flag or barcode is preserved, including when product `updatedAt` did not change.
- A replayed SQL acknowledgement is historical evidence, never authority for a second external send. Source/UUID/SKU reservations and immutable event records protect concurrent duplicate requests.
- Shopify product mutations do not offer general version CAS. The draft lease, fresh version/commercial comparison and unpublished scope reduce the external race; they are not a cross-system transaction.
- Image readiness uses exact frozen byte identity, not merely successful decoding. Shopify transformations that alter bytes remain under review in this conservative version. A later approved pixel-equivalence verifier is needed before treating transformed bytes as equivalent.
- Unknown price/tax/stock stay unknown. Draft creation does not prove sellability. Public activation, location-aware inventory and a binding/approval finalizer are separate and absent from this version.

## Incomplete intents, private persistence and editor (isolated candidate)

`src/lib/shopify/creation-intent.ts` supplies the pure preparation contract. `creation-intent-runtime.ts`, the private creation-intents route, the new-product editor and the additive pending-intent migration connect it to durable server-side saving and automatic draft promotion. No feature flag is activated by these changes.

- `saveCreationIntent(previous, input, serverEditContext, identityProof)` accepts an incomplete private item with explicit `null` values, empty media and undecided intent. It returns a candidate record and revision; the caller must persist it using an actual database CAS. A hash alone is not authentication or a transaction. The expected revision must be an own property containing explicit null for first save or the exact prior revision. A stale editor cannot silently replace another revision. Store SKU and manufacturer SKU can each be filled once; after assignment they remain exact and immutable. Corrections require a deliberate new identity/review workflow, not punctuation normalization.
- All edit provenance is derived from server-authenticated actor/request IDs and the server time. Unchanged fields retain their provenance; description text and rich HTML form one atomic field. Submitted references are explicitly unverified. No browser field can mark a manufacturer fact as verified. A differing manufacturer/store identifier needs the ID of an exact server-read verification receipt at freeze; it is never substituted into the store SKU.
- `assessCreationIntent` returns separate `draftBlockers` and `publicBlockers`. Missing currency, shipping decision, usable title, store SKU, brand, description decision or product image can remain saved in the private pending table. Missing selling price/tax/stock cannot imply public readiness. A known compare-at amount without a selling price also blocks the external draft until the relationship can be checked. Blank description/SEO is distinct from unknown/missing input.
- `freezeCreationIntent` rejects any existing binding or copy approval, including disabled approvals and explicit aliases; it reuses complete all-status Gallery/Shopify collision proof, unique custom-ID definition and decoded image proof from `creation-policy.ts`. The held Mandarina items and hidden Porsche identifiers remain excluded. `publish_when_ready` is retained privately but maps only to an external DRAFT request in v1. Inventory is still explicitly unknown. Location stock access, publication and final binding remain unavailable.
- `planCreationIntentRetry` checks that the frozen source revision is still current, then uses the existing immutable receipt/custom-ID state machine. A started or uncertain request is looked up, never reset to a second create. Later edits require review, not replacement of an already-started source.

### Persistence and authority

- `save_gallery_creation_intent` and `promote_gallery_creation_intent` use the existing shared advisory lock, bounded lock timeout, exact identity reservation and revision CAS. Incomplete saving never enters the copy outbox. Promotion and source freezing occur in the same transaction as reservation. The worker then freezes ordered decoded media evidence under its existing source/lease protocol before any external send.
- Pending records, immutable revision events and mapping receipts are private. The service role has table SELECT and narrow RPC execution only. The browser cannot insert or alter trusted mapping receipts. A missing receipt holds the saved item without replacing exact SKU identity.
- A trigger on the legacy draft reservation table verifies pending source and mapping authority, including direct service-role RPC calls. No-pending requests with different manufacturer/store identifiers or claimed mapping evidence are refused.
- The editor labels unknown stock and missing commercial inputs honestly. It derives no merchant price from manufacturer/supplier sources, and offers no publication operation.
